# AI长程记忆系统技术说明与交付定位

## 一、文档说明

本文档用于说明当前项目的建设目标、系统定位、交付范围、总体架构、研发流程、使用流程以及后续演进方向。文档面向项目负责人、技术管理者和后续维护人员，作为当前阶段的正式技术说明材料使用。

## 二、项目概述

本项目面向长期用户交互场景，建设一套可本地运行、可通过 API 接入、可持续评测和迭代的 AI 长程记忆系统。系统围绕记忆写入、结构化抽取、长期存储、检索重排、多证据聚合、反馈记录和离线复评等关键能力展开，目标不是做单次演示，而是形成可交付、可增强的工程化底座。

当前版本已经完成主链路打通，并补齐了与交付直接相关的能力，包括：

- 本地运行与 API 服务
- 多层记忆建模与存储
- 可切换检索后端
- feedback 记录机制
- 交互日志留存
- 离线复评数据导出
- benchmark 接入与分段验证

## 三、项目定位

### 3.1 建议采用的定位

当前项目建议定位为：

`AI长程记忆系统（含评测与迭代框架）`

这一定位同时覆盖以下两部分内容：

- 运行时记忆系统
- 评测与持续优化框架

### 3.2 不能只称为 harness

项目内部确实已经形成了较完整的评测与迭代 harness，但如果对外只称为 harness，会产生两个问题：

- 容易被理解为“只是一个测试框架”
- 无法体现当前已经具备的运行时记忆服务能力

因此，更准确的表达方式是：

`本项目是一套可运行的长程记忆系统，其内部同时包含一套用于正式评测和持续优化的 harness。`

### 3.3 为什么也不能只称为 demo

当前项目已经具备 API、配置、存储、日志、备份、反馈和评测能力，明显超出 demo 的范围。它已经不是临时展示代码，而是一个具备工程化形态的系统底座。

## 五、系统总体架构

### 5.1 架构原则

系统采用“运行时主链路 + 评测迭代链路”的双链结构。

运行时主链路负责真实用户请求处理。  
评测迭代链路负责问题定位、效果验证和后续增强。

### 5.2 运行时主链路

运行时主链路由以下环节组成：

1. 输入接收  
接收用户标识、会话标识和当前文本输入。

2. 结构化抽取  
从文本中提取标签、属性、关系、抽象概念和情绪信号。

3. 记忆写入  
将高价值输入写入长期记忆，并生成必要的 evidence span 或摘要性记忆。

4. 检索与重排  
从历史记忆中召回候选项，并基于多类特征完成重排。

5. 多证据聚合  
对列表型、总结型、跨轮型问题聚合多条证据，避免仅依赖单句命中。

6. 结果返回  
返回候选记忆、主结果以及必要的状态信息。

### 5.3 评测迭代链路

评测迭代链路由以下环节组成：

1. benchmark 数据接入  
当前已支持 LoCoMo、LangMemEval 及官方格式数据适配。

2. 分段评测  
支持 window 级、conversation 级和 batch 级验证。

3. 问题定位  
识别某一段 conversation、某一类题型或某一能力簇上的薄弱点。

4. 能力增强  
将问题反向映射到系统能力层，而不是按单题写死。

5. 回归验证  
在小窗、中窗、分会话和分批次上检查增强是否有效，是否引入回归。

### 5.4 检索后端设计

系统当前支持以下检索后端：

- `lexical`
- `semantic`
- `hybrid`
- `embedding_rerank`

当前默认后端为 `embedding_rerank`。  
系统已经支持通过配置文件和 API 切换后端，因此后续增强可以通过替换检索和重排能力来推进，而不必总是修改大量规则。

## 六、系统当前的核心价值

### 6.1 不是简单的关键词检索

系统不是只依赖关键词匹配，而是同时利用：

- 结构化属性
- 关系与标签
- 语义匹配
- 候选重排
- 多证据聚合

因此它具备比普通检索更强的长期记忆处理能力。

### 6.2 不是一次性实验代码

系统当前已经具备：

- API
- 存储
- 配置
- 日志
- 备份
- 交互数据导出

这使它具备了面向交付的工程形态。

### 6.3 不是黑盒高分展示

系统不是只报一个总分，而是具备：

- 分窗验证
- conversation 级定位
- batch 级对比

因此能够明确说明问题出现在什么位置，而不是只有一个笼统结果。

### 6.4 具备持续增强接口

当前版本已补齐三类对交付非常关键的接口：

- 可切换检索后端
- feedback 记录与反馈报告
- 日志留存与离线复评导出

这三项使系统在交付后仍具备继续演进的基础。

## 七、研发流程说明

当前项目的研发流程可以概括为以下六步。

### 7.1 需求拆解

先根据最初 idea 将“记忆系统”拆解为明确的工程模块：

- 输入与会话管理
- 结构化抽取
- 记忆写入
- 存储
- 检索与重排
- 多证据聚合
- 反馈与日志
- 评测与分析

### 7.2 最小闭环实现

优先打通以下主链路：

- 用户输入
- 记忆写入
- 记忆召回
- API 输出

这一阶段目标是保证系统能运行，而不是先追求 benchmark 高分。

### 7.3 评测框架接入

在主链路稳定后，接入 benchmark 与正式评测流程：

- LoCoMo
- LangMemEval
- 官方格式数据
- 分窗验证
- conversation 级验证
- batch 级验证

### 7.4 能力簇增强

系统优化按能力簇推进，而不是按单题推进。当前实际增强过的能力包括但不限于：

- 时间理解
- 关系与人物建模
- 偏好建模
- 跨轮聚合
- noisy query 处理
- mirrored query 处理
- answer style rerank

### 7.5 回归验证

每轮增强后，优先做受控验证：

- 小窗
- 中窗
- 分会话
- 分批次

这样可以减少长时间空跑，也便于快速发现回归问题。

### 7.6 交付收口

在交付前补齐以下产品化能力：

- 后端切换
- feedback 记录
- 日志留存
- 离线复评导出
- API 说明
- 存储与备份
- 技术文档

## 八、用户使用流程

### 8.1 部署阶段

部署人员需要完成以下工作：

- 配置存储路径
- 配置检索后端
- 启动 API 服务
- 配置日志与离线导出目录

### 8.2 运行阶段

系统上线后，用户每输入一条文本，系统执行以下流程：

1. 识别情绪与显著性  
2. 更新用户画像  
3. 写入长期记忆  
4. 召回相关历史记忆  
5. 对候选结果进行重排  
6. 返回结果和候选信息

### 8.3 反馈阶段

用户可以对系统返回结果提交以下反馈：

- `correct`
- `incorrect`
- `irrelevant`

反馈会写入反馈存储，并影响后续排序偏好。

### 8.4 运营与研发阶段

系统运行过程中会留存交互日志。研发或运营人员可以定期导出离线复评样本，用于：

- 分析系统错误
- 增补评测样本
- 调整后端或参数
- 支持下一轮增强

## 九、当前版本的边界

### 9.1 当前已经具备

- 本地部署与运行
- 长期记忆写入与召回
- 检索与重排
- 分段 benchmark 评测
- 会话级问题定位
- 后端切换
- feedback 记录
- 日志留存
- 离线复评导出

### 9.2 当前尚未完全具备

- 基于 feedback 的自动在线学习
- 面向中文真实场景的大规模系统化实测
- 基于更强大模型的复杂抽取与重排增强
- 多租户生产级部署能力
- 全自动训练与再训练流水线

因此，当前版本已经具备“交付底座”的条件，但仍然属于“可持续增强版本”，而不是能力完全封顶的终版。

## 十、后续演进方向

### 10.1 更强检索与重排能力

在当前可切换后端的基础上，引入更强的 embedding 模型和 rerank 模型，提高召回与排序上限。

### 10.2 中文场景增强

围绕中文真实用户使用场景继续补充：

- 中文 query routing
- 中文属性别名
- 中文时间表达处理
- 中文评测集

### 10.3 大模型增强接入

后续可以在以下环节接入大模型增强能力：

- 结构化抽取
- query routing
- rerank / judge
- summary / reflection

需要强调的是，大模型应当作为增强模块接入，而不是当前系统存在的前提。当前项目的价值在于先把记忆系统底座和评测框架工程化做扎实。

## 十一、建议的对外表述

建议采用如下表述：

`本项目构建了一套面向长期用户交互的 AI 长程记忆系统。系统具备结构化记忆写入、长期存储、检索重排、多证据聚合、反馈记录和离线复评能力；同时配套提供 conversation 级和 window 级评测框架，用于正式验证、瓶颈定位和持续优化。当前版本已完成本地运行、API 接入、后端切换、反馈留存和评测闭环，具备作为记忆系统底座交付和持续增强的条件。`

## 十二、结论

当前项目最准确的定位，不是单纯的 demo，也不是单纯的 benchmark harness，而是：

`一套可运行、可评测、可留痕、可持续增强的 AI 长程记忆系统底座。`

其中，评测 harness 是系统的重要组成部分，用于支撑后续评测、迭代和增强，但不应替代系统本身的整体定位。
