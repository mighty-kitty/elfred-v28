## 二、为什么会出现"放了代码但没用上"

1. **判定口径错**：早期状态只做探活（HTTP 200 就算"已连接"），把"服务活着"说成了"已经在用"。
2. **没有回执要求**：模块接进去时，没有要求"必须有一条真实调用的证据"，于是探活通过就交付了。
3. **代码位置散**：上游源码放在别的仓库，提交主库时只带了调用方，没带被调用方（同事那次"EMS/Skill Foundry 代码没放上去"就是这么来的）。

## 三、打通计划（每个闭环都要有验收证据）

| 顺序 | 闭环 | 具体动作 | 验收（缺一不算） |
| --- | --- | --- | --- |
| 1 | **EMOS 记忆同步** | 配 `ELFRED_MEMORY_HUB_TOKEN`（本地可用仓库里的 `services/emos-memory` + `elfred_bridge`，`ELFRED_MEMORY_HUB_AUTOSTART=true` 会自动拉起） | 写一条记忆 → `memory_bridge` 出现 `status=synced` → `/health/deps` 的 EMOS 显示 `used:true` 且 `last_used_at` 有值 |
| 2 | **Skill Foundry 生成** | 把"从一次真实任务/上下文生成一张 skill"接过去（产出 SKILL.md 落成 `skill` 对象），能力卡上标出来源 | 生成一次 → 能力卡组出现这张卡且标记"来自 Foundry" → `/health/deps` 显示 `used:true` |
| 3 | **PA 网关规划** | 把需要规划的任务交给网关出 `plan`，网关不可用时回落到应用内运行时 | 一次任务 → `run.plan` 来自网关（回执里带网关的 id） → 状态显示 `used:true` |
| 4 | **Jev 判定** | 按之前定的用法（记忆侧判定 / 检索重排）接一条真实流程，并显示用量 | 一次判定 → 回执含用量 → 状态显示 `used:true` |

## 四、以后立的规矩

1. **状态只认回执**：任何模块接进来，`/health/deps` 必须给出 `used` 与 `last_used_at`；只有探活不算接上。
2. **交付带闭环**：新模块的 PR 里必须有一条端到端测试（真实动作 → 真实回执 → 状态可查），否则不合并。
3. **源码与调用方同行**：上游模块的源码必须随主库一起提交（`services/` 已经在主库里，这条按它执行）。

**顺手修掉的两个坑（都是实测踩出来的）**：

1. **能力服务必须有它的上游 FreeTodo**：`POST /events/batch` 在没有 FreeTodo 时全部 `retry`、
   canonical task 恒为 0（根本起草不了）。本地做法：跑 `FreeTodo-main` 的
   `python -m lifetrace.server`（8001，需要 `PYTHONUTF8=1`，否则它读 `.env` 会按 GBK 报错），
   再让 Foundry 指向它（`FREETODO_BASE_URL=http://127.0.0.1:8001`）。这条依赖要写进部署说明。
2. **探活把"健康"误判成"不可达"**：Foundry 的 `/health` 会带整份上游状态（实测 45KB），
   而探针原来有 20KB 的体积上限 → 直接判不可达。已放宽到 200KB；现在健康时会正确显示
   `ok:true`。

接口已经找到：Foundry 暴露 `/v1/elfred/skills` 与 `/v1/elfred/skill-runs`
（`adapter/agent_routes.py`），本地控制面还带 CORS 白名单。计划：加一条命令
`skill.generate`（输入一次真实任务/上下文 → 让 Foundry 产出 SKILL.md → 落成 `skill` 对象，
带 `source:"foundry"` 与出处；不可用时回落为"未接通"，不假装）。

**接口侦察结果（2026-09-29，读 `services/skill-foundry/adapter/api.py`）**：

| 接口 | 用途 |
| --- | --- |
| `POST {prefix}/events`、`/events/batch`、`/import/json` | 把上下文事件喂给 Foundry（它自己落成 canonical task） |
| `GET {prefix}/jobs`、`/jobs/{id}` | 看它消化到哪里 |
| `POST {prefix}/skills/drafts/from-tasks`（body：`task_ids`、可选 `skill_id`） | **从一个或多个 canonical task 生成 skill 草稿**（后台任务） |
| `GET {prefix}/skills/builds/{build_id}` | 草稿生成进度 / 失败原因 |
| `GET {prefix}/skills/{skill_id}`、`GET {prefix}/skills` | 读生成的 skill（SKILL.md 内容） |
| `POST {prefix}/skills/{skill_id}/approve`、`/run`、`/skill-runs/{id}/feedback` | 审批、试跑、回收反馈 |

**⚠️ 关键约束**：`task_ids` 是 **Foundry 自己的** canonical task（int），不是我们对象库里的 task id。
所以真正接通要两半：

1. **喂事件**：把第二页/第四页的上下文（任务目标、验收结果、知识条目）按 `ContextEvent` 发到
   `POST {prefix}/events`，让 Foundry 生成自己的 task；
2. **取成品**：拿它返回的 task id 调 `drafts/from-tasks` → 轮询 `builds/{build_id}` → 读
   `skills/{skill_id}` → 落成我们的 `skill` 对象（带 `source:"foundry"` 与原样 SKILL.md 出处）。

第 1 半决定"它有没有东西可学"，第 2 半决定"我们能不能把它的产出变成能力卡"。两半都通了，
`/health/deps` 的 `skill_foundry` 才会显示 `used:true`。

**当时要你定的两件事（都已定并落地）**：

1. 入口放哪 → 已按建议放在第二页能力卡组右上「+」旁（手建的「创建工具」保留）；
2. Foundry 自报 `degraded` 怎么处理 → 已定：**先把它的上游 FreeTodo 配起来**（8001），
   否则 `events/batch` 全部 `retry`、canonical task 恒为 0，根本起草不了（实测结论）。

### 第三批：PA 网关规划 —— ✅ 已打通并验证

- 新模块 `server/elfred/pa-gateway/`：任务创建时，**多步骤/要分工**的目标会自动登记一次规划请求
  （判定写在 `needsGatewayPlan`：一句话里有先后步骤、或带协作分工）。命令只登记，
  真正的 HTTP 在运行时循环里做（`tickGateway`，和记忆同步、能力生成同一个位置）——
  ① 建一次本人档案 `POST /v1/pa/profiles`（幂等键按用户，工具范围随档案一起交给它）；
  ② `POST /v1/pa/{pa_id}/messages` 让网关规划，轮询 `GET /v1/runs/{run_id}` 取 `plan`；
  ③ 取到后取消它那条停在 waiting_approval 的运行，方案落成 `gateway_plan` 对象。
- **方案怎么用**：`run.start` 时把网关的方案翻成我们运行时的步骤（`stepsFromGatewayPlan`），
  翻得出来就采纳（`plan.plan_source="pa-gateway"`，回执里带网关的 run_id / planner / planning_ms），
  翻不出来或网关不可用就回落应用内计划（`plan.plan_source="in-app-runtime"`），
  并且**把它跳过了哪几步写进回执**（例如"网关拆成两次产出，这次合成一次成果生成"）。
  我们自己的独立复核 + 必要时修正这一段，任何来源的计划都必须带上。
- 关键约束：网关的工具名必须能落到我们真能执行的动作（`knowledge_search`→本地检索、
  `emos_recall`→读已授权资料、`task_create`→生成成果）。**建档案时就把这份清单交给它**
  （`tool_scopes`），它的规划器与策略都按这份清单出方案，不会规划出我们接不住的动作。
- 现场验证（真跑）：建一个"先查资料 → 比较三种方案 → 写对比报告"的任务 →
  运行时自动取回方案（`planner:"llm"`，`planning_ms` 634–1997，三次实测）→
  启动任务后 `plan.plan_source="pa-gateway"`，回执带 `run_id` 与采纳/跳过明细 →
  五个步骤全部成功（`ctx-1` 读取资料、`work` 生成成果、`review` 核对、`repair` 修订），
  停在等人验收（`awaiting_review`，结果不被说成已完成）→
  `/health/deps` 的 gateway 变成
  `ok:true · used:true · last_used_at:… · evidence:"已从它取回 N 次方案（共 M 步）"`。
- 回归测试：`tests/elfred/pa-gateway.test.mjs`（9 条：只有多步任务登记、没配地址不假装、
  取方案并与使用证据对上、落不成步骤时回落且点名、能落成时计划来自网关且复核不丢、
  网关连不上如实报错、工具范围变化要同步、没有授权资料不摆走过场步骤、拆分产出合成一次但写明）。

### 第四批：Jev 判定 —— ✅ 已打通并验证

- 新模块 `server/elfred/jev-verdict/`：**自动学到的理解**（低风险直接生效的那些）都排一次 Jev 核对，
  判定条件固定三条：① 是不是用户本人的长期要求（不是一次性安排）② 有没有超出原句范围 ③ 原句是不是疑问/假设/转述。
- 判定结果落在理解对象上（`jev`：判定 id、模型、三条判定与依据的那一行原话、用量）；
  三条里出现"明确不支持"时，这条理解**降级为待本人确认**（不再自动当已学到的理解用），
  并写明是哪条条件不支持。判定为"满足"时只记判定，不擅自把它升级成事实。
- 与记忆同步同一个路子：记忆写入时登记请求，运行时循环里发 HTTP（`tickJev`）；
  Jev 没配置就留着不判（不假装判过）。
- 现场验证（真跑，真 Jev API）：说一句"我平时写方案喜欢先给结论，再补依据。" →
  应用把它学成一条理解 → Jev 真判一次（`model:"jev-1.13.0"`，
  `usage: 1742 + 264 = 2006 tokens`，三条判定各自带依据行）→
  `/health/deps` 的 Jev 变成
  `configured:true · used:true · last_used_at:… · evidence:"已用它核对 1 条理解（合计 2006 tokens）"`。
- 回归测试：`tests/elfred/jev-verdict.test.mjs`（6 条：该核对的才登记、没配置不判、
  明确不支持要降级并带用量、满足不越权升级、判定不完整就报错不改理解、自动学习时已排好核对）。

### 2026-09-29 审计轮的三个修正（都在我们自己的模块里）

1. **规划方案只给"还没跑的、用户自己的"多步骤任务**。原来在 `task.create` 那一刻登记，
   而对话回复 / 群内回复 / 朋友圈点评这类系统流程的"我是内部流程"标记是**创建之后**才附上任务的，
   它们的 run 又在同一个命令里就启动 —— 结果是：**用户只发一句聊天，也会白花一次网关规划调用**
   （实测：干净账号只聊天，网关却显示"已在用"）。现在登记改在运行时循环里按状态扫
   （`gatewayCandidate`：草稿 / 待启动 + 非内部标记 + 目标多步；已跑起来的不补，
   放了两天没人动的草稿也不补），判定逻辑全在我们模块里，不再去改宿主的对话流程文件。
   实测：只聊天的账号 → 网关"未使用"；用户自己建的多步骤任务 → 方案照常出并被采纳。
2. **设置页的 Jev 那行补上"已在用 / 未使用"**：其他四行都有这个标记，只有它漏了，
   和"状态只认回执"的口径不一致。
3. 静态审计工具 `tools/page2-checks/audit.mjs` 进仓库；顺手修掉两处乱码注释、
