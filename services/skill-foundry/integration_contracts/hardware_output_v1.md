# Elfred Hardware Output Contract v1

This contract separates Journal generation from physical-device integration. The
computer runs one Elfred Adapter service. Pendant, base, robot arm, and printer
are four logical adapters behind that service.

## Journal-ready input

When the Journal is generated inside this Adapter, a successful non-dry-run
payload automatically creates an idempotent Hardware Output plan. This is a
sidecar operation: it does not alter the Journal response, does not queue a Run,
and cannot make Journal generation fail. Disable it with:

```text
ELFRED_HARDWARE_AUTO_PLAN_ON_JOURNAL=false
```

If Hardware Output itself is disabled, Journal remains a software-only feature
with its previous response contract.

For a Journal produced by another process, push the completed payload:

```http
POST /v1/elfred/hardware-output/journals/ready
Content-Type: application/json
```

```json
{
  "journal": {
    "journalId": "journal-2026-07-30",
    "journalVersion": "v2",
    "date": "2026-07-30",
    "title": "Personal Journal",
    "content": "Combined Journal text",
    "contentObjective": "Objective record",
    "contentAi": "Personal reflection",
    "mood": "疲惫",
    "energy": 2,
    "tags": ["Elfred"]
  },
  "planningMode": "auto",
  "executeSafeActions": false
}
```

Or plan a Journal that is already in FreeTodo:

```http
POST /v1/elfred/hardware-output/journals/{journal_id}/plan
```

If the collaborator changes the Journal storage location, only the
`JournalSnapshot` source mapping changes. Planning and all device adapters remain
unchanged.

Memory is not required by contract v1. `HardwareMemoryPort` is an optional future
port for preference lookup and execution feedback; the default implementation
is a no-op.

## Device bridge

An HTTP device or vendor-SDK bridge implements:

```text
GET  /health
POST /command
POST /stop
```

Example command:

```json
{
  "protocolVersion": "1.0",
  "runId": "hrun_...",
  "actionId": "haction_...",
  "adapterId": "base",
  "command": "play_scene",
  "preset": "calm_evening",
  "parameters": {
    "mood": "疲惫",
    "energy": 2
  }
}
```

The bridge returns a JSON object with device-specific diagnostics. HTTP 2xx means
the command was accepted and completed for v1. The device must treat `actionId`
as an idempotency key so a network retry cannot repeat a physical action.

Known commands:

| Adapter | Command | Current presets |
| --- | --- | --- |
| `pendant` | `notify` | `journal_ready` |
| `base` | `play_scene` | `welcome_home`, `calm_evening` |
| `arm` | `run_preset` | `fetch_coat`, `diagnostic` |
| `printer` | `print_journal` | `daily_journal`, `diagnostic` |

The robot arm never receives coordinates generated by a model. It receives only
a calibrated preset and always requires explicit confirmation.

## Local configuration

Copy `config/hardware_output.example.json` to
`config/hardware_output.local.json`. The local file is ignored by Git.

```json
{
  "devices": {
    "base": {
      "transport": "http",
      "baseUrl": "http://192.168.1.52",
      "healthPath": "/health",
      "commandPath": "/command",
      "stopPath": "/stop",
      "headers": {
        "Authorization": "Bearer local-secret"
      }
    }
  }
}
```

Devices left as `mock` remain fully testable without hardware. Do not commit
addresses, tokens, Journal data, printer output, or diagnostic captures.

For the validated XIAO ESP32-S3 Wi-Fi firmware, use `transport: "xiao"` instead
of the generic HTTP bridge. It reuses `/api/status` and `X-Xiao-Token`, requires
the firmware to advertise `elfred-xiao-command-v1`, and reserves separate
`/api/hardware/*` routes so stream control cannot be confused with a physical
action. See `integration_contracts/xiao_hardware_command_v1.md` and
`config/hardware_output.xiao.example.json`.

## Execution API

```text
POST /v1/elfred/hardware-output/plans/{plan_id}/execute
GET  /v1/elfred/hardware-output/runs/{run_id}
POST /v1/elfred/hardware-output/runs/{run_id}/retry
```

Safe actions can run while the arm remains `confirmation_required`. A later
request supplies the arm action ID in `confirmedActionIds`.

## Remote diagnostics

```text
GET /v1/elfred/hardware-output/doctor
GET /v1/elfred/hardware-output/support-bundle
```

The support bundle deliberately excludes Journal text, command parameters,
adapter headers, and secrets.
