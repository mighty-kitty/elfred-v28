# 调研：第一张能力卡，到底该怎么问

日期：2026-09-29。起因：用户真机走了一遍三步初始化，反馈"**选起来很吃力**"，并提出两个问题：
① 前面的题是不是应该随着选择而变化？② 别人的产品真的是这么引导的吗？
本文只做三件事：核现在的流程、看别人怎么做（可考证）、给一个能落地的改法。**不含代码改动。**

## 1. 我们现在问的是什么（真机实拍 + 代码）

| 屏 | 屏幕上的东西 | 必答项 |
| --- | --- | --- |
| 1 | 一句话标题 + 五组共 15 张预置卡（单选）+「其它」一句话 | 选 1 张卡，或写一句 |
| 2 | 一句话标题 + 四组偏好（先给结论／先给过程 · 简短／详细 · 引用来源 · 独立复核） | 4 组都要读一遍 |
| 3 | 预览这一张卡 + 一句"Lv.1 发现、0 成果" | 无 |

三个问题，按严重程度排：

1. **屏 1 给的是"我们能做什么"的目录。** 用户得先读懂五个系统（探索／参谋／创作／连接／执行），
   再把自己的需求翻译成我们的分类。这是一道"学习我们的产品"的题，不是"说出你要什么"的题。
2. **屏 2 的四组偏好与屏 1 的选择无关。** 无论选"查资料并核实来源"还是"安排一次日程"，
   进第二屏看到的都是同样四组题——所以它读起来像填表，而不像在描述"我要的这张卡"。
   这正是"前面的题是不是也应该随选择变化"这个疑问的来源：**确实没有联动**。
3. **屏 2 问的其实是我们该学的。** "先给结论还是先给过程""要不要引用来源"这类偏好，
   本来就是我们**理解度／记忆**要在使用里学的东西（被指正会扣分那套）。开局让用户自己填一遍，
   等于让用户替系统做功课，而且他此刻还没有依据回答。

## 2. 别人的产品怎么做（读了源码／看了首屏，不是猜）

### LobeHub（开源，今天核过 `main` 分支）

- 步骤只有六个：Telemetry → ResponseLanguage → FullName → **Interests** → ProSettings → **AgentPicker**
  （`src/features/Onboarding/steps/`）。
- 全程只有一步问"内容"：`InterestsStep` 给 17 个兴趣领域，**多选、可跳过**。
- 它拿到兴趣之后**不是写文案**，而是 `interestCategoryMap.ts` 的 `interestsToCategoryHints()` →
  变成下一步的**分类提示**，用 `getTemplatesByCategoryPriority()` 给 Agent 市场**排序和筛选**
  （`steps/AgentPickerStep/index.tsx`）。**选框的作用是"决定下一步给你看什么"。**
- 最后一步是**装现成的 Agent**（`installMarketplaceAgents`），不是现场生成一张卡。
- 全程**没有**"你要它先给结论还是先给过程"这类偏好题。

### Hyperknow

- 登录后首屏是一句话 + 一个输入框，框里**预填一条示例**（"Look into my Canvas, and generate…"），
  旁边只有附件和 Tools。
- 没有选框引导：它靠**例子**教会用户怎么提要求，用户只需要说自己的目标。

### ChatGPT 的自定义 GPT（对照，非源码）

- 建一个 GPT 是**对话式**的：你说要它干什么，它替你写名字、说明、开场问题；
  细节都收在「Configure」里，需要才展开。既不是从一堆分类里挑，也不问偏好。

### 横向看下来，共同点是

| 它们做 | 它们不做 |
| --- | --- |
| 用一句话／一段示例让用户说出**目标** | 让用户先学产品的分类体系 |
| 选框只用来**决定接下来给你看什么**（筛选器） | 把选框当问卷，收集与下一步无关的信息 |
| 偏好靠**使用中学习**、或收进"想改再改"的高级项 | 开局面向新手问"你要它怎么工作" |
| 结束时"能用 + 有事可做" | 结束时只是"设置好了" |

我们的三步里，第 1 步和第 3 步是对的（选框 → 生成一张可用卡 + 一条任务草稿），
**错在第 2 步**：它既不随选择变化，又是我们该学的东西。

## 3. 三个可选做法

### A（推荐）一句话开头，其余全默认，想改再改

| 屏 | 屏幕上的东西 | 必答项 |
| --- | --- | --- |
| 1 | 一句话输入框（带示例占位）+ 一行小字入口「或者从常见的事里挑一件」→ 展开 15 张卡（默认收起） | 说一句话，或点一张卡 |
| 2 | 预览："它属于「洞察」维度 · 能替你做什么 · 交付是什么" + 两个动作：**就这样生成**／**改一改** | 无 |
| 3 | 「改一改」展开后才出现：改名字、改归属系统、四组偏好（默认值已填好） | 无 |

要点：

- 必答从"选 1 张 + 读 4 组题"降到**一句话或一次点击**。
- 四组偏好从"必答"降级为"想改再改"，默认值直接进说明书——**该学的交给使用过程**。
- 预览里**把系统的推断显示出来**（维度 + 用途 + 交付），用户看到的是"它把我说的理解成了什么"，
  而不是自己填一堆字段。你问的"通过我的选择判断我的 skill 属于哪方面、里面有什么"，
  这一步其实就是现在的实现（归属系统 + 模板说明书），只是**没让用户看见**。

### B 保留 15 张卡，但让第二屏**随卡而变**

- 选中某张卡后，第二屏只问**与这张卡相关**的一两个问题，例如：
  「查资料并核实来源」→ 资料范围（只看我给的 / 允许联网 / 两者都行）；
  「整理群聊里的行动项」→ 待办要不要顺带落到日程。
- 好处：真的"随选择变化"，而且每题都有依据可答。
- 代价：15 张卡各写 1~2 道追问的文案与映射（文案量不小），而且**问题依然是我们该学的**。

### C 不初始化，先用起来再沉淀

- 空态只留一个输入框；用户第一次真做完一件事，再据此沉淀第一张卡。
- 与 9-27 会议口径相反（纪要明确要摒弃纯文本对话引导），且用户短期看不到"能力卡"这个东西。

## 4. 结论与建议

走 **A**，并把 B 的"随选择变化"作为「改一改」里的可选路径保留：

- 选框不删（口径不推翻），但从"必答目录"降级为"给不想写字的人的快捷方式"，
  并且**选中后只显示与它相关的信息**（维度 / 用途 / 交付），不再问四组通用偏好。
- 四组偏好收进「改一改」，默认值直接进说明书与记忆；以后靠使用中的指正去学习和修正。
- 结束时仍然是"一张可用卡 + 一条任务草稿"，与现有实现一致，后端不用动。

**要动的东西**（前端为主，`app/v28/features/pages24/parts/card-onboarding.tsx`）：
第一步改成"输入框优先、选框可展开"；第二步合并预览与"想改再改"；三步变两步。
预置卡目录、模板生成、服务端命令都不变。

**自测口径**：初始化探针（`tools/page2-checks/onboarding-audit.mjs`）按新流程重写——
① 只写一句话就能生成一张卡；② 一句话里能推出归属系统；③ 不动「改一改」时四组偏好取默认值且进了说明书；
④ 展开「改一改」改一项，说明书随之变化；⑤ 只用选框（不写字）走通；⑥ 生成后仍然是一张可用卡 + 一条草稿。

## 5. 落地记录（2026-09-29 当天）

最后没有走 A/B/C 里的任何一条原样，而是把 A 的"一句话"和 B 的"随选择变化"合起来，
按用户的要求改成了**分支选择树**：每页 3 个选项、选完决定下一页、路径决定**内容**（不只是卡）。
所以"同一张卡走不同路径 = 两份不同的 skill"。上面第 3 节里"选框是筛选器"那半句仍然成立：
选项既筛出下一步问什么，也往这张卡的说明书里写内容片段。

实现与口径见 `docs/设计-第一张能力卡初始化流程-v1.md` §10.2。

- Hyperknow：官网与演示首屏（App 在 `agent.hyperknow.io`，需登录）。
